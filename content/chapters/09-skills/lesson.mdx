## 1. Skills 是什么

<RealStep
  id="skill-concept-understood"
  command=""
>
  读完这一节，理解 Skill 和一次性脚本的区别，然后点「我跑完了」。
</RealStep>

Ch 7 里你写了 `invoice_ocr.py`——一个一次性脚本，处理完这批发票就束之高阁了。

但有些工作是**每月都要做的**：整理本月发票、对账银行流水、准备季末税务资料……

每次都要重新向 Claude 解释「我要整理发票，步骤是这样的，格式是那样的」——太麻烦了。

**Skill 是什么？** Skill 就是你写给 Claude 的「工作说明书」：把这件重复工作的背景、步骤、注意事项写成一个 `SKILL.md` 文件，放到指定位置。下次你只要说「帮我整理本月发票」，Claude 就会自动找到这份说明书，按照它来做。

<Callout type="insight" title="Skill vs 一次性任务：本质区别">

**一次性 Python 脚本**（Ch 7 那种方式）：

- 你描述需求 → Claude 写代码 → 你跑代码
- 每次任务可能不同，代码往往只用一次

**Skill**（这一章的方式）：

- 你写一份说明书（`SKILL.md`）→ Claude 读了之后知道「这类请求对应这套流程」
- 说明书长期有效，以后同类请求都会自动触发，不用每次重新解释

类比：与其每次告诉同事「去便利店帮我买一瓶矿泉水，要冰的，不要超过 3 元」，不如给他一张「我的日常采购清单」贴在冰箱上。
</Callout>

### 什么时候该用 Skill？

✅ **适合写成 Skill 的**（重复、多步、跨工具）：

- 月初整理本月发票 → 固定流程，每月做一次
- 银行流水自动分类 → 固定规则，反复使用
- 季末税务申报准备 → 步骤多，容易遗漏

❌ **不适合写成 Skill 的**（一次性、问答型）：

- "帮我解释什么是应收账款" → 直接问 Claude 就好
- "帮我写一段 Python 计算个税" → 一次性任务，用 `claude` 直接说就够

## 2. 写第一个 Skill：organize-invoices

### 目录约定

Claude Code 会自动扫描 `~/.claude/skills/` 目录下所有子目录里的 `SKILL.md` 文件。格式很简单：

```
~/.claude/skills/
└── organize-invoices/
    └── SKILL.md
```

每个子目录对应一个 Skill，目录名就是 Skill 的名字。

### SKILL.md 的结构

一个有效的 `SKILL.md` 包含两部分：

1. **YAML frontmatter**（`---` 之间）— 机器读的：`name` 和 `description`
2. **Markdown 正文** — 人读的：解释「什么时候用」和「步骤是什么」

`description` 是最重要的字段——Claude 根据这段描述判断你的请求是否应该触发这个 Skill。写得越贴近你平时说话的方式，自动识别成功率越高。

### 动手：创建 organize-invoices Skill

<RealStep
  id="skill-file-written"
  command="mkdir -p ~/.claude/skills/organize-invoices && nano ~/.claude/skills/organize-invoices/SKILL.md"
>
  **推荐做法：用 `nano` 在终端里直接创建文件。**

  在终端里依次跑这两步——第一步建目录，第二步打开编辑器：

  ```bash
  mkdir -p ~/.claude/skills/organize-invoices
  nano ~/.claude/skills/organize-invoices/SKILL.md
  ```

  `nano` 会全屏打开一个空文件。把下面 SKILL.md 的内容**整段复制粘贴**进去，然后:

  - **Ctrl + O** → 按回车确认文件名 → **保存**
  - **Ctrl + X** → 退出 nano

  退出 nano 之后,在终端跑一句 `cat ~/.claude/skills/organize-invoices/SKILL.md` 确认内容写进去了,然后点「我跑完了」。

  <Callout type="tip" title="SKILL.md 完整内容（整段复制）">

  ````markdown
  ---
  name: organize-invoices
  description: 整理本月的发票PDF/图片 — OCR提取 + 按商家汇总到 Excel。适合每月初做月报前用。
  ---

  # organize-invoices

  ## 何时使用

  当用户说要"整理本月发票"、"做发票汇总"、"按商家汇总发票"时，使用这个 skill。

  ## 「本月」的判定

  - **默认按 OCR 提取的发票 `fields.date.value` 字段**(ISO 格式 `YYYY-MM-DD`)筛选当月。例如今天是 2026-05-25,就只挑 `date.value` 落在 `2026-05-01`～`2026-05-31` 的发票。
  - **如果某张发票 `fields.date.value` 是 `null`**(`aa-ocr` 没识别出日期,常见于扫描质量低或手写发票):回退到**文件 mtime**(文件最后修改时间)来判断它属于哪个月。
  - **跨月发票的处理**:4 月底开的发票 5 月才拿到,按 OCR `date` 走的话归 4 月(开票月),不会出现在 5 月汇总里。如果用户期望按**收到的月份**归类(账期口径),要在用户明确说明时改用 mtime 或用户输入的账期月份;否则保持开票月口径。

  ## 步骤

  **步骤 0:检查必备目录存在**(避免第一句话就崩):

  ```bash
  if [ ! -d "$HOME/accounting-learner/invoices" ]; then
    mkdir -p "$HOME/accounting-learner/invoices"
  fi
  if [ ! -d "$HOME/accounting-learner/outputs" ]; then
    mkdir -p "$HOME/accounting-learner/outputs"
  fi
  ls "$HOME/accounting-learner/invoices"/*.pdf "$HOME/accounting-learner/invoices"/*.png "$HOME/accounting-learner/invoices"/*.jpg 2>/dev/null | head -1
  ```

  - 如果 `invoices/` 不存在 → 自动建一个空目录(让脚本不至于第一句话就崩)。
  - 如果 `invoices/` 是空的 → 上面的 `ls` 会没有输出,这时 Skill 应该**报「`~/accounting-learner/invoices/` 里没有 PDF/PNG/JPG,请把发票文件放进去再跑」并退出**,不要继续往下做。
  - 如果 `outputs/` 不存在 → 一样自动建。

  **步骤 1:打印启动标记**(证明 Skill 已被加载):

  ```bash
  echo "🔹 organize-invoices v1 启动 — 时间 $(date '+%H:%M:%S')"
  ```

  **步骤 2-7:核心流程**

  2. 列出 `~/accounting-learner/invoices/` 目录里所有 PDF/PNG/JPG 文件
  3. 对每个文件用 `aa-ocr <file>` 做 OCR,拿到 JSON(注意 JSON 总是输出到 stdout,无论退出码)
  4. 从 JSON 里解析:
     - `fields.date.value` → 日期(可能为 null)
     - `fields.vendor.value` → 商家
     - `fields.amount.value` → 金额
     - `fields.tax_id.value` → 税号
  5. **按「本月」判定规则过滤**:`date.value` 落在当月的留下;`date.value` 为 null 的看 mtime 落在当月的也留下;其余跳过(归到「不属于本月」单独提示一下)。
  6. 按 `vendor`(商家)分组求和,输出到 `~/accounting-learner/outputs/invoice_summary_organize-invoices-v1_<YYYY-MM>.xlsx`
  7. 任何 OCR 失败(exit 3)或部分字段(exit 4)的发票,单独列在「需手填」sheet 里(文件名 + 已识别到的字段 + 缺失的字段标记)

  ## 注意

  - 不要修改原始发票文件
  - 输出文件名包含 `organize-invoices-v1` 版本标记,便于以后审计是哪个版本的 Skill 生成的
  - 中文表头:**日期 / 商家 / 金额 / 税号**(4 列,**不要凭空生成「类目」**——会计科目需要人工判断,Skill 不要乱猜)
  ````

  </Callout>

  <Callout type="insight" title="为什么不用「让 Claude 帮你创建文件」的方式">
  早期版本的这一章曾经推荐过「在 REPL 里粘贴一整段含 `---` frontmatter 的 message,让 Claude 帮你写文件」的方法。但实际跑下来,zsh 和 Claude Code REPL 对**多行粘贴 + 单引号 + `$()` + YAML 三连横杠**的处理非常容易翻车——少一个反引号、转义一个字符就让 SKILL.md 写歪,而且失败方式还不明显。

  `nano` 虽然看起来"老派",但它就是最简单可靠的方式:你看到什么,文件里就是什么。把翻车风险降到 0。
  </Callout>
</RealStep>

<Callout type="tip" title="description 是触发的关键">
`description` 字段决定 Claude 在什么情况下会想到这个 Skill。写的时候想象一下：你平时会怎么描述这项任务？把那些词放进 `description` 里。

示例中的 "整理本月的发票 PDF/图片" 和 "适合每月初做月报前用" 都是触发词——贴近你真实的说话方式。
</Callout>

## 3. 让 Claude 自动调用 Skill

<RealStep
  id="skill-invoked-by-claude"
  command="claude"
>
  开一个**全新的 Claude 会话**（不要用 `--continue`），然后用自然语言触发 Skill。为什么开新会话：让 Claude 用 SKILL.md 说明书从干净的起点开始，而不是继续上次的对话上下文 —— 上次会话可能没读过你新写的 SKILL.md。

  在终端里运行 `claude`，然后说：

  ```
  帮我整理本月的发票
  ```

  注意：**不要**说「用 organize-invoices skill 帮我整理」——那样就失去了 Skill 的意义。应该用自然语言描述任务，让 Claude 自己识别。

  正常情况下，Claude 会先执行步骤 1 的启动标记命令，你能在终端看到一行：

  ```
  🔹 organize-invoices v1 启动 — 时间 14:23:07
  ```

  然后它会开始运行 `aa-ocr` 并处理文件。

  **客观验证标准**（两项都要满足，缺一不可）：

  1. **终端能看到** `🔹 organize-invoices v1 启动` 字样——证明 Skill 步骤 1 真的跑了，不是 Claude 嘴上随便说说。
  2. **生成的输出文件名包含** `organize-invoices-v1`（例如 `invoice_summary_organize-invoices-v1_2026-05.xlsx`）——这是 Skill 留下的"作案痕迹"，文件存档后还能查到是哪个版本生成的。

  两个都看到了再点「我跑完了」。如果 Claude 只是嘴上说"我用了 organize-invoices skill"但终端没有 🔹 那行启动标记，说明 Skill 其实没被加载，要回去检查 SKILL.md 文件路径是否正确。
</RealStep>

<Callout type="warn" title="如果 Claude 没有自动调用 Skill">
可能的原因：

1. **description 写得不够贴近你的请求**：回去修改 `~/.claude/skills/organize-invoices/SKILL.md` 的 `description` 字段，让它更接近你实际说话的方式。
2. **会话没有完全重新启动**：确保退出了之前的 Claude 进程，再开一个全新的 `claude` 会话。
3. **目录路径有误**：检查 `~/.claude/skills/organize-invoices/SKILL.md` 文件是否真实存在（用 `ls ~/.claude/skills/` 确认）。

Skills 的触发不是魔法——Claude 在读 `description` 时做语义匹配。把 description 写得越像你的真实请求，匹配越准。
</Callout>

## 4. 在真实发票上测试

<RealStep
  id="skill-tested-on-real-data"
  command="ls ~/accounting-learner/invoices/"
>
  把几张真实发票（PDF 或 PNG/JPG 格式）放入 `~/accounting-learner/invoices/` 目录，然后重新开一个 Claude 会话，说「帮我整理本月的发票」，让 Skill 完整跑一遍。

  **检查输出**：

  1. 终端里看到 `🔹 organize-invoices v1 启动` 启动标记（证明 Skill 步骤 1 真的执行了）
  2. `~/accounting-learner/outputs/` 目录里出现了 `invoice_summary_organize-invoices-v1_<当月>.xlsx` 文件（文件名带版本标记）
  3. Excel 文件里有正确的中文表头：日期 / 商家 / 金额 / 税号（4 列）
  4. 如果有识别失败的发票，它们出现在「需手填」sheet 里
  5. 原始发票文件没有被修改（Skill 说明里写了「不要修改原始文件」）

  全部确认后，点「我跑完了」。
</RealStep>

<Callout type="warn" title="OCR 识别不准？用 Ch 8 的方法修改 Skill">
如果 `aa-ocr` 对某些发票字段识别有偏差（比如税号漏了几位、金额格式不对），不要手动改输出——而是用 Ch 8 学的四段式 BugReportCard 方法，把问题描述给 Claude，让它在 `SKILL.md` 的「步骤」或「注意」里增加纠错说明。

例如：「aa-ocr 对手写发票的金额字段经常返回 null，帮我在 Skill 里加一步：遇到金额为 null 时，把文件名列入「需手填」sheet，并打印提示」。
</Callout>

<Callout type="insight" title="Skill 是活的说明书，会随使用成长">
第一次写的 SKILL.md 不会是完美的——用多了你会发现新的边界情况：某类发票格式不对、某月文件数量太多、某些字段命名习惯不一样。

每次发现新问题，就回去往 SKILL.md 里加几行说明。这就是「活文档」——不是一次性写完的，而是随着使用慢慢完善的。
</Callout>

## 5. 什么时候该写 Skill，什么时候不该

| | 任务类型 | 建议 |
|---|---|---|
| ✅ | 月初整理发票（重复、多步、跨工具） | 写成 Skill |
| ✅ | 银行流水自动分类（重复、有标准做法） | 写成 Skill |
| ✅ | 季末税务申报准备（重复、步骤多） | 写成 Skill |
| ❌ | 解释什么是「应收账款」（一次性问答） | 直接问 Claude |
| ❌ | 写一段 Python 计算个税（一次性任务） | 直接让 Claude 写，不需要 Skill |

**判断标准**：如果你发现自己每次对 Claude 说的话都差不多（同样的任务、同样的步骤、同样的格式要求），那就值得写成 Skill。如果每次任务都不一样，直接说就够了。

## 6. 进阶：Skills 只是开始

Skill 是 Claude Code 三种「行为扩展」方式里最轻量的一种：

| 机制 | 适合做什么 | 何时学 |
|---|---|---|
| **Skill** | 给 Claude 写任务说明书，让它更聪明地理解你的重复任务 | 本章（Ch 9） |
| **Hook** | 在 Claude 完成某个操作前后自动运行你的代码 | Ch 10 |
| **MCP** | 让 Claude 接入外部工具（数据库、API、文件系统） | Ch 10 |

下一章（Ch 10）我们会看 Hooks 和 MCP——它们让 Claude 不只是「聪明」，还能「接入你的工具链」。
