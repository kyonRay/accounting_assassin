## 1. 从「逐步确认」到「一键批量」

Ch 11 里你用 Codex 完成了单个 CSV 的分类——每一次文件读写，Codex 都会询问你是否批准。

这种方式适合探索性任务：你可以在每步确认，随时叫停。

但现在场景变了：你有 **6 个月的银行流水 CSV**，每个文件都要做同样的分类。如果每个文件触发 5 次工具调用，那就是 **30 次确认点击**。重复、机械，正是 AI 应该替你做的事。

**解决方案：`codex exec`**

`codex exec` 是 Codex 的非交互式批量模式。你给它一个任务描述，它自动完成所有文件操作，不弹任何确认框，最后把结果汇报给你。

这是一把利器——也是一把需要提前做好保护的利器。

---

## 2. 第一步：在动手之前，先给工作区拍张快照

**这是本章最重要的习惯**：每次使用自动审批模式之前，先提交一次 Git 快照。

为什么？因为 `codex exec` 会自动修改、创建文件，不经过你的逐步确认。如果 AI 理解偏差，或者任务描述有歧义，它可能在工作区里产生一批你不想要的文件。有了快照，用一条命令就能完全恢复。

没有快照，"撤销"这件事就没有了明确的目标——你不知道回退到哪里。

<RealStep
  id="workspace-snapshotted"
  command="cd ~/accounting-learner && git add -A && git commit -m 'snapshot before batch run'"
>
  在终端里运行上面的命令，把当前工作区的全部内容存档到 Git。

  **如果你的工作目录还没有初始化 Git 仓库**（比如从 Ch 6 开始就没用过 Git），先跑这两条：

  ```bash
  cd ~/accounting-learner
  git init && git add -A && git commit -m "initial snapshot"
  ```

  **如果你的工作区是干净的**（没有未追踪的修改），`git status` 会显示 `nothing to commit`——这也是好事，说明工作区已经处于干净状态。可以直接进行下一步。

  <Callout type="insight" title="Ch 8 教过的这条命令">
  你在第 8 章学过 `git restore .`——那是出了问题之后的撤销命令。  
  现在学的 `git commit` 快照，是**出问题之前**的保护动作。

  规则很简单：**每次让 AI 自动跑批量任务之前，先 commit 一下**。
  </Callout>

  快照提交成功（或确认工作区已干净）后，点「我跑完了」。
</RealStep>

## 3. 第二步：准备批量处理的文件

这一步有两种情况：你已经有真实的银行流水文件，或者你用 Codex 生成练习用的样例文件。

**无论哪种，目标都一样**：在 `~/accounting-learner/data/raw/` 目录里，放 4-6 个 CSV 文件，每个文件代表一个月的流水记录。

<RealStep
  id="batch-input-prepared"
  command="ls ~/accounting-learner/data/raw/"
>
  **选项 A：生成样例 CSV（推荐——如果你没有真实文件）**

  在 `~/accounting-learner` 目录下启动 Codex（交互式模式），告诉它：

  ```
  帮我在 data/raw/ 目录下生成 5 个样例银行流水 CSV 文件，
  文件名格式是 bank_2026-0N.csv（N 从 1 到 5），
  每个文件包含 6-8 行记录，格式：日期,摘要,金额(元)
  摘要内容随机混合：餐厅、滴滴、快递、超市、办公用品、停车费、外卖
  ```

  Codex 会在 `data/raw/` 目录里创建好全部文件。

  **选项 B：使用真实文件**

  如果你有实际的银行流水 CSV（记得先脱敏处理，去掉账号、姓名等敏感信息），直接复制到这个目录：

  ```bash
  mkdir -p ~/accounting-learner/data/raw/
  # 然后把你的文件拖进去，或者用 cp 命令复制
  ```

  ---

  确认目录里有至少 4 个 CSV 文件后，运行上面的 `ls` 命令验证，然后点「我跑完了」。
</RealStep>

## 4. 第三步：用 `codex exec` 自动处理全部文件

现在是核心操作：用 `codex exec` 一次性处理所有 CSV 文件。

`codex exec` 的基本语法是：

```bash
codex exec --sandbox workspace-write "你的任务描述"
```

- `--sandbox workspace-write`：允许 Codex 在工作目录里读写文件，不需要每步确认
- 引号里的内容是你的任务描述（可以很长，很具体）

<Callout type="tip" title="关于 --full-auto 标志">
你可能在较早的教程里看到过 `codex --full-auto` 这个写法。这个标志在当前版本里已经废弃，运行时会打印警告。  
现在推荐的写法是 `codex exec --sandbox workspace-write`，功能完全相同。  
如果你不确定自己安装的版本支持哪些选项，运行 `codex --help` 查看完整列表。
</Callout>

<RealStep
  id="auto-approve-tried"
  expectsCli="Codex"
  command="cd ~/accounting-learner && codex exec --sandbox workspace-write \"帮我把 data/raw/ 目录下的所有 CSV 文件，按支出类目分类，每个文件输出到 data/classified/ 目录，文件名加上 _classified 后缀\""
>
  在终端里运行上面的命令（注意引号是命令的一部分）。

  **你会观察到和 Ch 11 完全不同的执行方式**：

  - Codex **不会弹出确认框**——它直接开始读文件、处理、写文件
  - 多个文件可能**并行处理**——Codex 会同时派出多个子任务，分别处理不同文件
  - 等待期间你只需要看着——没有任何操作需要你来批准
  - 完成后 Codex 会给你一份汇报：处理了哪些文件、创建了哪些输出

  **验证结果**：

  ```bash
  ls ~/accounting-learner/data/classified/
  # 应该看到和 data/raw/ 里数量相同的 *_classified.csv 文件
  ```

  用 `ls` 确认输出文件都生成了之后，点「我跑完了」。

  <Callout type="tip" title="如果 Codex 报错「找不到文件」">
  确保你在 `~/accounting-learner` 目录下运行命令（不是在 `~` 根目录）。  
  Codex 用相对路径 `data/raw/` 定位文件，工作目录不对会找不到。
  </Callout>
</RealStep>

## 5. 第四步：理解「什么时候不该用 auto-approve」

`codex exec` 是效率工具，不是万能工具。下面这四条规则，是使用自动审批模式的安全底线：

<RealStep
  id="safety-rule-understood"
>
  仔细阅读下面四条规则，想一想每条对应你实际工作里的哪种场景。

  ---

  **规则一：有 Git 快照才能用**

  `codex exec` 对文件的修改是不可撤销的——除非你有 Git 快照。  
  每次批量任务之前，先 `git commit`。出了问题，`git restore .` 一条命令完全恢复。

  参考 **Ch 8** 教过的这个工作流：
  - 批量跑之前 → `git add -A && git commit -m "snapshot before batch run"`
  - 出了问题 → `git restore .` （撤销所有未提交修改）
  - 如果还创建了新文件 → `git clean -i`（交互式逐一确认删除）

  ---

  **规则二：破坏性操作永远不用**

  以下情况**绝对不使用** auto-approve 模式：

  - 发送邮件、消息（发出去收不回来）
  - 调用支付 API（钱转出去了）
  - 删除工作区以外的文件（影响系统）
  - 执行数据库 DELETE / DROP（数据永久消失）

  如果你的任务描述里涉及这些操作，用交互式 `codex` 替代，逐步确认每一步。

  ---

  **规则三：任务描述要精确**

  自动模式没有确认环节——如果描述有歧义，AI 可能做出和你想象完全不同的事。

  差的描述：`"帮我处理一下 data 目录里的文件"`  
  好的描述：`"把 data/raw/ 里所有 *.csv 文件，按类目分类后输出到 data/classified/，文件名加 _classified 后缀，不要修改 raw/ 里的原始文件"`

  用 `codex exec` 之前，把任务描述写得跟交代给新同事一样详细。

  ---

  **规则四：工作区边界不变**

  `codex exec --sandbox workspace-write` 的权限范围是你的工作目录（`~/accounting-learner/`）。  
  Codex 无法访问这个目录以外的文件——这是本课程 **三条文件系统边界** 之一（你在 Ch 5 学过）。  
  但在工作区内，auto-approve 模式下 Codex 有完全的读写权限。Git 快照是你在工作区内的唯一防线。

  ---

  <Callout type="insight" title="风险管理，不是恐惧管理">
  这四条规则不是在吓你——而是让你在用 `codex exec` 时**知道自己在做什么**。

  一位经验丰富的会计处理完整账册之前，一定会先把原始凭证存档，留一份备份。  
  Git 快照 + 精确的任务描述，就是 AI 时代里那份"备份"的概念。

  掌握了这套风险管理方式，`codex exec` 就是你手里真正强大的工具。
  </Callout>

  读完四条规则，对照自己的场景思考一遍之后，点「我跑完了」。
</RealStep>

## 本章回顾

| 里程碑 | 意义 |
|---|---|
| 提交 Git 快照 | 用 auto-approve 之前的必做保护动作 |
| 准备批量 CSV 文件 | 有了可以重复处理的真实输入 |
| 跑 `codex exec --sandbox workspace-write` | 亲手体验批量自动处理的效率跳跃 |
| 理解四条安全规则 | 知道什么时候可以放心用，什么时候必须退回交互式 |

**`codex exec` vs 交互式 `codex` 的选择**：

| 场景 | 选哪个 |
|---|---|
| 探索新任务、还不确定方向 | 交互式 `codex`（逐步确认） |
| 明确的、重复的批量文件操作 | `codex exec --sandbox workspace-write` |
| 涉及邮件/支付/删除系统文件 | **永远不用 auto-approve** |
| 工作区没有 Git 快照 | 先 commit，再考虑 exec |
