如果你没有 ChatGPT Plus / Pro 订阅，**Claude Code 有类似的能力**，但具体参数不一样——见 Ch 6-10。粗略的对照如下：

| 概念 | Codex | Claude Code |
|---|---|---|

## 1. 从「盯着每一步」到「一键批量」

Ch 11 里你用 Codex 完成了单个 CSV 的分类——Codex 会把每一步工具调用都展示给你看，你能盯着过程，觉得不对就随时叫停。

这种方式适合探索性任务：单个文件、未知结果，看着每一步反而踏实。

但现在场景变了：你有 **6 个月的银行流水 CSV**，每个文件都要做同样的分类。如果每个文件触发 5 次工具调用，那就是 **30 次盯屏幕等它跑完**——重复、机械，正是 AI 应该替你扛过去的部分。

**解决方案：`codex exec`**

`codex exec` 是 Codex 的非交互式批量模式。你给它一个任务描述，它自动完成所有文件操作，不弹任何确认框，最后把结果汇报给你。

这是一把利器——也是一把需要提前做好保护的利器。

---

## 2. 第一步：在动手之前，先给工作区拍张快照

**这是本章最重要的习惯**：每次使用自动审批模式之前，先提交一次 Git 快照。

为什么？因为 `codex exec` 会自动修改、创建文件，不经过你的逐步确认。如果 AI 理解偏差，或者任务描述有歧义，它可能在工作区里产生一批你不想要的文件。有了快照，用一条命令就能完全恢复。

没有快照，"撤销"这件事就没有了明确的目标——你不知道回退到哪里。

<Callout type="warn" title="先告诉 Git：不要碰真实数据">
**银行流水里有客户姓名、卡号、金额**。如果这个仓库以后给同事看，或者推到 GitHub，这些数据就泄露了——Git 历史里删都删不干净。

所以在 `git add -A` **之前**，先告诉 Git 哪些目录永远不要纳入版本控制：

```bash
cd ~/accounting-learner
cat >> .gitignore <<'EOF'
# 真实账务数据——永远不进 Git
data/raw/
data/classified/
outputs/
*.csv
*.xlsx
EOF
git add .gitignore
git commit -m "ignore real accounting data"
```

这样下面这一步做 `git add -A` 快照时，Git 只会收录脚本、Skill、Hook 这些**代码资产**，而不会把数据文件写进历史。
</Callout>

<RealStep
  id="workspace-snapshotted"
  command="cd ~/accounting-learner && git add -A && git commit -m 'snapshot before batch run'"
>
  **顺序**：先按上面 Callout 里的步骤创建 `.gitignore` 并提交一次，**然后**再运行上面这条 `git add -A` 命令做快照。

  这样快照里只有代码（脚本、Skill、Hook），没有真实的银行流水或客户数据。

  **如果你的工作目录还没有初始化 Git 仓库**（比如从 Ch 6 开始就没用过 Git），先跑这两条，再做 `.gitignore` 和快照：

  ```bash
  cd ~/accounting-learner
  git init
  ```

  **如果你的工作区是干净的**（没有未追踪的修改），`git status` 会显示 `nothing to commit`——这也是好事，说明工作区已经处于干净状态。可以直接进行下一步。

  <Callout type="insight" title="Ch 8 教过的这条命令">
  你在第 8 章学过 `git restore .`——那是出了问题之后的撤销命令。  
  现在学的 `git commit` 快照，是**出问题之前**的保护动作。

  规则很简单：**每次让 AI 自动跑批量任务之前，先 commit 一下**（前提是 `.gitignore` 已经挡住了真实数据）。
  </Callout>

  `.gitignore` 提交完成 + 工作区快照提交成功（或确认工作区已干净）后，点「我跑完了」。
</RealStep>

## 3. 第二步：准备批量处理的文件

这一步有两种情况：你已经有真实的银行流水文件，或者你用 Codex 生成练习用的样例文件。

**无论哪种，目标都一样**：在 `~/accounting-learner/data/raw/` 目录里，放 4-6 个 CSV 文件，每个文件代表一个月的流水记录。

## 4. 第三步：用 `codex exec` 自动处理全部文件

现在是核心操作：用 `codex exec` 一次性处理所有 CSV 文件。

`codex exec` 的基本语法是：

```bash
codex exec --sandbox workspace-write "你的任务描述"
```

- 引号里的内容是你的任务描述（可以很长，很具体）
- `--sandbox workspace-write` 是关于**权限**的——下面会展开

### 「不弹确认框」到底是哪里来的？两条独立的轴

很多人把 `--sandbox` 和「不弹确认框」混为一谈。这是错的。Codex 里有 **两条独立的轴**，你要分清：

| 轴 | 控制什么 | 标志 |
|---|---|---|
| **权限轴**：能改哪些文件 | Codex 能在哪里写文件（只读 / 工作区 / 任意位置） | `--sandbox <mode>` |
| **审批轴**：动手前要不要问你 | Codex 执行命令前是否暂停等你点「同意」 | `--ask-for-approval <mode>` |

- `--sandbox`：可选值是 `read-only` / `workspace-write` / `danger-full-access`。它只回答「Codex 可以**改哪里的**文件」。
- `--ask-for-approval`：可选值是 `untrusted` / `on-request` / `never`。它只回答「Codex 动手前**要不要先问你**」。

**关键事实**：

- **交互式 `codex`**（不带 `exec`）默认会弹确认框——即使你加了 `--sandbox workspace-write`。因为 `--sandbox` 不是审批轴的开关，审批轴的默认是 `untrusted`（陌生命令要问）。
- **`codex exec`** 是 Codex 的**非交互式子命令**，本身就是设计来跑脚本、跑批量的——它「不弹确认框」是因为这个子命令是非交互的，不是因为 `--sandbox` 标志做了什么。
- 在 `codex exec` 下加 `--sandbox workspace-write`，只是把权限范围放开到工作目录；如果你不加，默认还是只读，AI 会尝试写文件然后失败。

换句话说：

- **「能写工作目录」** 来自 `--sandbox workspace-write`
- **「不暂停问你」** 来自 `codex exec` 这个子命令本身

两件事要一起到位，本章这条命令才能批量自动跑通。

<Callout type="tip" title="关于 --full-auto 标志">
你可能在较早的教程里看到过 `codex --full-auto` 这个写法。这个标志在当前版本里已经废弃，运行时会打印警告。  
现在推荐的写法是 `codex exec --sandbox workspace-write`，效果相同。  
如果你不确定自己安装的版本支持哪些选项，运行 `codex --help` 查看完整列表。
</Callout>

<Callout type="insight" title="更推荐的做法：先 codex 进交互模式，再粘 prompt">
**不用 `codex exec` 一行命令塞 prompt，而是先 `codex` 进交互模式，再粘贴 prompt。**

**好处：** 你能看到 Codex 在做什么、随时按 Ctrl+C 中断、prompt 改起来不用纠结引号转义（中文引号 / 嵌套引号 / 多行换行在一行命令里都是地狱）。

**`codex exec` 适合场景：** 写到脚本里、cron 调度、CI/CD 触发。**临时手动跑就用交互式。**

下面那条 `codex exec ...` 命令保留作为参考，让你看到非交互式的完整形态——但首次手动跑，强烈建议先 `codex` 进 REPL，再把任务描述粘进去。
</Callout>

  | 现象 | 原因 | 处理 |
  |---|---|---|

  | `not logged in` 或 `subscription required` | Codex 登录过期 / 订阅没了 | `codex login` 重登；订阅过期参考 Ch 11 顶部「用 Codex 之前必须知道的事」 |
  | `Please tell me who you are`（git commit 错） | 没设 git user.name / user.email | `git config --global user.email "you@example.com" && git config --global user.name "你的名字"` |
  | AI 跑完了，怎么核对？ | 没法肉眼一行行看 | 让 Claude 跑一个 sanity check：`读 outputs/ 下所有文件，产 JSON 报告：总行数、各类目笔数、最大金额 top 5、可疑值。` 和 Ch 14 的 AI 校验同款。 |

## 5. 第四步：理解「什么时候不该用 auto-approve」

`codex exec` 是效率工具，不是万能工具。下面这四条规则，是使用自动审批模式的安全底线：

<RealStep
  id="safety-rule-understood"
>
  仔细阅读下面四条规则，想一想每条对应你实际工作里的哪种场景。

  ---

  **规则一：有 Git 快照才能用（而且 `.gitignore` 必须先挡住真实数据）**

  `codex exec` 对文件的修改是不可撤销的——除非你有 Git 快照。  
  每次批量任务之前，先 `git commit`。出了问题，`git restore .` 一条命令完全恢复。

  > **`git restore .` + `git clean -i` 在 Ch 8 详讲过了**（`git restore .` 回滚已追踪文件的修改，`git clean -i` 交互式删除未追踪的新文件）。本章规则一就是 Ch 8 那套「后悔药」工作流的 Codex 版本——这里不重复教学，只交叉链接。

  参考 **Ch 8** 教过的这个工作流，**再加上本章开头的 `.gitignore` 前置步骤**：
  - 一次性准备 → `.gitignore` 里写好 `data/raw/` `data/classified/` `outputs/` `*.csv` `*.xlsx`，单独提交一次
  - 批量跑之前 → `git add -A && git commit -m "snapshot before batch run"`（此时只会收录代码，不会收录真实数据）
  - 出了问题 → `git restore .`（撤销所有未提交修改，Ch 8 §3）
  - 如果还创建了新文件 → `git clean -i`（交互式逐一确认删除，Ch 8 §4）

  ---

  **规则二：破坏性操作永远不用**

  以下情况**绝对不使用** auto-approve 模式：

  - 发送邮件、消息（发出去收不回来）
  - 调用支付 API（钱转出去了）
  - 删除工作区以外的文件（影响系统）
  - 执行数据库 DELETE / DROP（数据永久消失）

  如果你的任务描述里涉及这些操作，用交互式 `codex` 替代，逐步确认每一步。

  ---

  **规则三：任务描述要精确**

  自动模式没有确认环节——如果描述有歧义，AI 可能做出和你想象完全不同的事。

  差的描述：`"帮我处理一下 data 目录里的文件"`  
  好的描述：`"把 data/raw/ 里所有 *.csv 文件，按类目分类后输出到 data/classified/，文件名加 _classified 后缀，不要修改 raw/ 里的原始文件"`

  用 `codex exec` 之前，把任务描述写得跟交代给新同事一样详细。

  ---

  **规则四：工作区边界不变**

  `codex exec --sandbox workspace-write` 的权限范围是你的工作目录（`~/accounting-learner/`）。  
  Codex 无法访问这个目录以外的文件——这是本课程 **三条文件系统边界** 之一（你在 Ch 5 学过）。  
  但在工作区内，auto-approve 模式下 Codex 有完全的读写权限。Git 快照是你在工作区内的唯一防线。

  ---

  <Callout type="insight" title="风险管理，不是恐惧管理">
  这四条规则不是在吓你——而是让你在用 `codex exec` 时**知道自己在做什么**。

  一位经验丰富的会计处理完整账册之前，一定会先把原始凭证存档，留一份备份。  
  Git 快照 + 精确的任务描述，就是 AI 时代里那份"备份"的概念。

  掌握了这套风险管理方式，`codex exec` 就是你手里真正强大的工具。
  </Callout>

  读完四条规则，对照自己的场景思考一遍之后，点「我跑完了」。
</RealStep>

## 本章回顾

| 里程碑 | 意义 |
|---|---|
| 提交 Git 快照 | 用 auto-approve 之前的必做保护动作 |
| 准备批量 CSV 文件 | 有了可以重复处理的真实输入 |
| 跑 `codex exec --sandbox workspace-write` | 亲手体验批量自动处理的效率跳跃 |
| 理解四条安全规则 | 知道什么时候可以放心用，什么时候必须退回交互式 |

**`codex exec` vs 交互式 `codex` 的选择**：

| 场景 | 选哪个 |
|---|---|
| 探索新任务、还不确定方向 | 交互式 `codex`（逐步确认） |
| 明确的、重复的批量文件操作 | `codex exec --sandbox workspace-write` |
| 涉及邮件/支付/删除系统文件 | **永远不用 auto-approve** |
| 工作区没有 Git 快照 | 先 commit，再考虑 exec |
