## 1. 认识你的第二位 AI 同事

到目前为止，Claude Code 一直是你的 AI 搭档。从第 11 章开始，你要认识一位新同事：**Codex CLI**（由 OpenAI 出品）。

**重要前提：Codex 不是"Claude 2.0"。**

它们是两个来自不同公司、设计理念略有差异的 AI 编码助手，就像两个都很能干、但工作风格不同的同事：

| | Claude Code | Codex CLI |
|---|---|---|
| 出品方 | Anthropic | OpenAI |
| 交互风格 | 倾向多问一句确认意图 | 倾向直接给方案，但动手前会问 `Approve?` |
| 工具调用展示 | 较详细，实时滚动 | 更紧凑，完成后汇报 |
| 适合场景 | 对话探索、边想边做 | 明确任务、批量处理 |

> **注意**：网上有些旧资料说 "Codex 直接动手不问"——这个说法已经过时了。**当前版本的 Codex CLI 在写文件、跑命令之前都会弹一个 `Approve?` 询问框**，跟 Claude Code 的确认提示很像，只是措辞不同。第 3 节安装完之后你会亲眼看到。

两者**没有优劣之分**——都是你工具箱里的工具。本章目标是：装上它、跑一次真实任务、感受一下它的工作风格。

如果你没有上述订阅，请参考本章顶部的降级说明——用 Claude Code 演示同样的任务，回头再补 Codex 部分。

你也可以用 OpenAI API Key 登录（无需 ChatGPT 订阅，但需要在 platform.openai.com 充值）。真实的命令格式是先把 key 放到环境变量，再通过 stdin 传给 `codex login`：

```bash
export OPENAI_API_KEY=sk-...        # 你的 API key（一次性配置）
printenv OPENAI_API_KEY | codex login --with-api-key
```

> 注意 `codex` 没有 `--provider` 或 `--api-key` 这种参数——API key 是通过 `codex login --with-api-key` 子命令配合 stdin 传入的。网上若有教程写 `codex --provider openai --api-key sk-...`，那是旧版本的格式（或道听途说），按上面这两行走才对。
</Callout>

## 4. 提前打个预防针：Codex 会问你 "Approve?"

下一步你就要让 Codex 真正动手写文件了。在那之前必须知道一件事：

**Codex 每次要写文件、跑命令之前，都会先在终端里弹一个询问框**，大概长这样：

```
┌─ Approve command? ─────────────────────────────────┐
│  codex wants to run: write file outputs/bank_…csv  │
│                                                     │
│  [y] yes    [n] no    [a] always allow in session   │
└─────────────────────────────────────────────────────┘
```

具体长相会因为 Codex 版本不同略有差异，但**关键词就是 `Approve?`、`yes/no`、`y/n`** 这几个。

**第一次看到的时候不要慌**，按这三步走：

1. **先看 Codex 想做什么**——它会写明要读哪个文件、要跑哪条命令
2. **判断有没有问题**——本章的任务只是读 CSV、写新 CSV，没问题
3. **按键回应**：
   - 同意 → 按 `y` 或回车
   - 不同意 → 按 `n`，Codex 会停下来问你怎么改
   - 本次会话里都同意 → 按 `a`（之后这次会话里同类操作就不会再问了，会话结束后失效）

<Callout type="tip" title="为什么 Codex 要问？这不是麻烦吗？">
这是 **AI 编码工具的安全设计**——即使你（用户）相信 AI，AI 也会在动手前问你一句，避免它误读你的意图、改坏了文件。

- Claude Code 也有类似机制，只是触发条件和措辞不同（比如它经常先描述「我要做 X」再动手）。
- 如果你做特别明确、低风险的批量任务（比如本章的 CSV 分类），可以按 `a` 让本次会话一路 `always`——但**养成"先看一眼再确认"的习惯**，比按惯性瞎确认安全多了。

第 12 章会更详细地讲 Codex 的「审批模式」（approval mode），包括 `--ask-for-approval` 参数怎么调，以及什么时候用 `--full-auto`（默认不要碰）。
</Callout>

知道这件事之后，下面的真实任务里看到 `Approve?` 提示就不会被吓到了。

## 5. 第一次真实任务：银行流水分类

### 任务背景

你每月都有一份银行流水 CSV，里面几十行收支记录，每行都需要打上支出类目（餐饮、交通、快递、办公、其它）。这是会计工作里最枯燥的重复任务之一——Codex 很擅长做这类事。

### 如果你还没有银行流水 CSV

没关系。先让 Codex 帮你生成一份样例 CSV 用来练习：

```
帮我在 outputs/ 目录下生成一个 bank_2026-04.csv 文件，
包含 6 行样例银行流水数据，格式：日期,摘要,金额(元)
摘要内容包含：餐厅、滴滴、京东快递、办公用品、外卖、停车费
```

生成完之后再做下面的分类任务。

### 动手：跑分类任务

<RealStep
  id="codex-first-task-tried"
  command="cd ~/accounting-learner && codex"
>
  打开终端，进入工作目录启动 Codex，然后对它说：

  ```
  帮我看看 outputs/bank_2026-04.csv，
  按支出类目把每一行归类（餐饮/交通/快递/办公/其它），
  输出新文件 outputs/bank_2026-04_classified.csv，
  新文件在原有列后面增加一列「类目」
  ```

  **观察 Codex 的工作过程**：
  - `Approve?` 询问框是不是按你预想的方式出现？回应 `y` 之后多久看到结果？
  - 工具调用（读文件、写文件）是怎么展示的？比 Claude Code 紧凑还是详细？
  - 完成后它怎么汇报结果？是详细列表还是简短总结？

  任务完成、看到 `bank_2026-04_classified.csv` 生成之后，输入 `/exit` 或按 `Ctrl+C` 退出，然后点「我跑完了」。

  <Callout type="tip" title="Codex 提示「No such file」？">
  如果 Codex 说找不到 CSV 文件，先按上面「生成样例 CSV」的提示让它创建一份，然后再试分类任务。

  也可以把自己真实的银行流水 CSV（手动脱敏处理后）放到 `~/accounting-learner/outputs/` 目录里。
  </Callout>
</RealStep>

## 6. 观察工作风格差异

这一步不需要在终端里操作——只需要回想刚才跑 Codex 的体验，对照下面的几条观察。

<RealStep
  id="style-noticed"
>
  回想一下刚才 Codex 完成任务的过程，思考以下几点：

  **你可能注意到了：**

  1. **方案给得更直接**——Codex 拿到任务后通常不会先反问「你确定要这样做吗？」，而是迅速给出执行计划。但**真正动手写文件之前，它依然会用 `Approve?` 询问框等你确认**。Claude Code 则倾向于先用自然语言确认意图，再申请工具调用。

  2. **工具调用展示更紧凑**——Codex 的 Read/Write/Bash 调用通常在一个折叠面板里，任务结束后才展开摘要。Claude Code 是实时流式展开。

  3. **错误时的行为不同**——Codex 遇到缺失文件、权限问题时，可能直接给出修复方案再请你 `Approve`；Claude 通常会先停下来用自然语言告诉你发生了什么、问你想怎么处理。

  4. **两者都不是"更好"**——Codex 的"先给方案、动手前确认"风格在明确任务时效率高；Claude 的"先讨论再动手"风格在探索性任务时更安全。

  <Callout type="insight" title="两个 AI 同事，不同的工作节奏">
  把 Claude Code 想象成一个做事谨慎、喜欢先讨论方案的同事；
  把 Codex 想象成一个接到任务先列出执行步骤、每一步动手前再请你点头的同事。

  两种风格都有价值——关键是根据任务性质来选择：
  - 探索性任务、不确定方向时 → Claude Code
  - 明确的批处理任务、重复操作时 → Codex
  </Callout>

  读完上面的内容，感受到这两种风格的差异之后，点「我跑完了」。
</RealStep>
